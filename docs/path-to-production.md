## 1. 真实身份验证（主网 Concordium ID）

**当前状态**
- demo 使用 testnet 身份提供商签发的**简化身份**（占位信息，链上可核实但不对应真实个人），
  仅用于 testnet 演示；testnet 上身份与账户体系与主网隔离。
- Agent 徽章（Verified by Concordium）绑定的是 owner 的链上身份；testnet 徽章在主网无任何效力。

**缺口**
- 主网身份必须走**实名验证**（真实证件 + 活体，由主网身份提供商签发），testnet 简化身份
  不可迁移、不可复用；owner 与运营主体须以真实身份重新完成主网 ID 签发。
- 运营主体的法律形态未定：以个人还是公司名义持有主网身份、开立账户，直接影响后续
  托管资金的合规资格（见 §3），须先决策再申请。
- 两个 agent 在主网重新注册：合约坐标不同（主网 CIS-8004 index 10082、CIS-8 index 10081，
  与 testnet 的 12802/12801 不同，已实测对照），Card 须以主网参数重新生成、托管、钉哈希。

## 2. Facilitator 运营与资金 / 密钥管理

**当前状态**
- facilitator 为自托管 Node 服务（无官方公共端点）：环境变量 + 密钥文件配置，密钥只进内存、
  不打印、不走命令行；无钥或钥格式错误时明确报错拒绝启动。
- dry-run 已证明 verify/settle 的形状与 9 条赞助交易规则的离线预校验可用；其中规则 2
  （身份绑定）与规则 8（签名验真）明确标注 requires-chain，live 时由 SDK 对链决定。

**缺口**
- **密钥管理**：demo 的密钥文件（600 权限、不进仓库）只适用于 testnet。生产须迁移到
  KMS/HSM 或等效托管，配套密钥轮换、最小权限、访问审计与灾备恢复流程；facilitator 私钥
  一旦泄露，攻击者可滥用赞助账户余额。
- **资金管理**：facilitator 以自有 CCD 垫付每笔结算的赞助手续费，需要独立的资金池、
  余额水位监控与自动/手动补充流程；垫付额度、单笔与日累计上限、异常熔断均未实现。
- **运营可用性**：当前是单进程本地服务，无高可用、无限流、无多实例；生产形态需要
  部署、扩缩容与故障切换方案。facilitator 是收付之外的第三方账户这一协议要求，
  在生产上还意味着运营主体与交易双方的利益隔离须可证明。
- **真实往返未验证**：第一笔真实 testnet settle 尚未跑过（等私钥导出），SDK 联签、
  提交与最终确定的时延与失败模式未知，须在 testnet 先完成并记录。

## 3. 合规与争议处理

**当前状态**
- demo 的 escrow 是**链下内存账本**（testnet 语境内的记账实现），不持有真实资金，
  不构成对任何人的托管服务；哈希链提供不可篡改的计量与审计轨迹，收据以 Ed25519 签名
  绑定金额、义务笔数、审计链头与交易哈希。
- 网站与文档口径已定：不虚构客户、交易量与上线状态，示例一律标注。

**缺口**
- **托管资质**：生产 escrow 若持有用户资金，可能触及支付/托管牌照与资金隔离要求，
  须按运营主体所在法域做正式法律评估；当前无公司主体、无牌照，此项是上线前置条件，
  不是工程任务。
- **争议裁决**：谁担任 escrow 运营方、交付争议如何裁决（退款/释放的裁量规则、举证、
  时限、申诉）目前只有设计笔记级别的考虑，未形成规则文本与流程实现；demo 的
  release/refund 只是状态机，不含争议分支。
- **AML/KYC 与法币出入口**：结算核心的生产形态（链下引擎 + 法币上下车）只存在于规划；
  法币通道的 KYC/AML、制裁筛查、交易限额与可疑交易报告义务均未接入。
- **数据与记录保存**：哈希链与签名收据满足「可审计」的工程基础，但保存年限、监管调阅
  格式、用户数据（GDPR 等）的处理规则未定。

## 4. 监控与审计

**当前状态**
- 审计链 `verify()` 可全链复算验真；离线 demo 与 dry-run 均把验真结果作为断言输出。
- facilitator 的离线预校验对每条规则给出 pass / fail / requires-chain 的逐条结论。

**缺口**
- **运行时监控**：无指标、告警与日志聚合；生产须监控 facilitator 余额水位、verify/settle
  成功率与时延、链上最终确定状态、escrow 账本与链上余额的定时对账（reconciliation），
  并对账不一致时自动冻结结算。
- **审计落地**：审计链目前在单进程内存/本地文件语境；生产须持久化、异地备份，并定义
  第三方审计的导出与验证方式（收据验签工具需对外可用，评委/审计方能独立复算）。
- **事件响应**：密钥泄露、异常大额、批量失败等场景的应急预案与联系人链未建立。

## 5. 主网上线步骤（建议顺序）

1. **决策与主体**：确定运营主体与法域，完成托管/支付合规评估（§3），再启动主网身份实名（§1）。
2. **主网身份与账户**：主网实名 ID 签发 → 建 owner / 买方 / 卖方 / facilitator 主网账户拓扑，
   facilitator 账户注入运营资金并设定水位告警（§2、§4）。
3. **主网注册**：以主网合约坐标（CIS-8004 10082 / CIS-8 10081）重新生成两张 Agent Card，
   逐字节托管 → 注册点签 → 徽章核验 → set_agent_uri 钉哈希；全流程先在 testnet 把
   待办的注册与真实结算完整走一遍并留档，作为主网操作的演练记录。
4. **密钥与部署**：facilitator 私钥迁入 KMS/HSM，服务按生产形态部署（限流、熔断、
   对账、监控告警齐备后才开 live）。
5. **灰度**：小额、邀请制对手方先行，争议规则文本与申诉通道同步上线；对账无差异、
   争议流程演练通过后再扩大范围。
6. **持续义务**：记录保存、定期第三方审计、密钥轮换与应急演练纳入运营日历。
