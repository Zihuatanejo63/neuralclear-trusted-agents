## 2. @x402/concordium SDK 调研

### 2.1 包与版本
- npm 包名：**`@x402/concordium`**（x402 Foundation 官方仓 `x402-foundation/x402` 的 monorepo 包，Apache-2.0）。
- 版本：官方仓 main 分支 package.json 为 **2.32.0**（2026-11-26 查）。npm 页本身抓取被拒（403），**npm 上 latest 标签的精确版本未直查核实**，安装时以 `npm view @x402/concordium version` 实测为准；第三方结算器项目（Integra settler）把 x402 系列包钉在 2.31.0 使用，可作兼容性参照。
- 依赖：`@concordium/web-sdk` ^12.0.0、`@x402/core`。导出子路径：`./exact/client`、`./exact/server`、`./exact/facilitator`。
- 语言支持（docs.x402.org SDK Features，2026-11-12 更新）：ccd 网络 **仅 TypeScript ✅，Go ❌、Python ❌**。这是路线取舍的决定性事实。

### 2.2 一笔 testnet x402 付款的完整流程（官方包 README 口径）
网络标识：testnet CAIP-2 = `ccd:4221332d34e1694168c2a0c0b3fd0f27`（主网 `ccd:9dd9ca4d19e9393877d2c44b70f89acb`）；节点 gRPC：`grpc.testnet.concordium.com:20000`（TLS）。机制：`exact` 方案，资产转移方式 = **sponsored V1**（Protocol 10 赞助交易）。

1. 买方请求资源 → 卖方服务器返回 **402 + PaymentRequirements**，其中 `extra.feePayer` 是 facilitator 的赞助账户（由 facilitator 的 `/supported` 宣告、服务器在 `enhancePaymentRequirements()` 时填入）。
2. 买方客户端（`ExactConcordiumScheme` client）从节点取 sender nonce，构建一笔 **V1 赞助交易**（原生 CCD 是 SimpleTransfer，PLT 是 TokenUpdate；金额以 microCCD 等原子单位计，CCD 6 位小数），把 facilitator 写为 sponsor，**只签 sender 一侧**（sponsor 签名槽留空），客户端不广播。
3. 买方把 `{ signedTransaction, sender }` 作为 PAYMENT-SIGNATURE 载荷发给服务器；服务器转交 facilitator `verify()`：**9 条规则**（版本=1、sender 身份、sponsor 身份须为 facilitator 本人、收款方=payTo、金额精确相等、资产类型、有效期 ≤10 分钟、sender 签名对链上 credential 验签、载荷安全=单一操作且 sponsor 不得是 sender/收款方）。
4. facilitator `settle()`：复验 → **补上 sponsor 签名 → 提交上链 → 等待 ConcordiumBFT 最终确定**（默认 requireFinalization=true，超时 60s；最终确定约 10s）→ 再做一次链上收发方复核 → 返回 SettleResponse，服务器放行资源。

**谁签名**：买方账户签转账本身（Ed25519，`buildBasicAccountSigner(私钥)`）；facilitator 以 sponsor 身份联签并**用自己的 CCD 付手续费**。买方只需持有付款金额的 CCD，不必另备手续费。

### 2.3 Facilitator 是谁 —— ⚠️ 无官方公共端点，按自托管设计
- x402.org 的默认公共 facilitator 支持列表（Base Sepolia、Solana Devnet、Algorand/Stellar/Aptos/Hedera/XRPL testnet 等）**不含 ccd**；Concordium 官方文章只说「合作伙伴在建 Concordium 上的 x402 facilitator」，未给出公共端点。**结论：未发现可直接用的官方公共 facilitator（截至 2026-11-26 查询），demo 须自托管。**
- 自托管不难：`@x402/concordium/exact/facilitator` 现成实现，只需一个 facilitator 账户（`CCD_FACILITATOR_ADDRESS` + `CCD_FACILITATOR_PRIVATE_KEY`），账户里备少量 test CCD 付费。
- **硬约束（verify 规则 9）**：sponsor 不得等于 sender、也不得等于收款方 → facilitator 必须是独立于买/卖双方的**第三个账户**。

### 2.4 资产选择
原生 CCD 与 PLT（EURR/USDR 等）都支持。本项目用**原生 test CCD** 最简：无须申请发行 PLT（testnet PLT 要走官方表单人工发放）。

### 2.5 运行环境要求
- Node.js + TypeScript（包以 tsx/tsup 工具链发布，CJS+ESM 双格式）；`@concordium/web-sdk` v12。
- 客户端签名需要账户**地址 + Ed25519 私钥**（环境变量 `CCD_ADDRESS` / `CCD_PRIVATE_KEY`）。即 demo 里的买方、卖方（收款可不签，但 settle 复核要地址）、facilitator 三个账户中，凡要签名的（买方付款、facilitator 赞助）都得有可用私钥——这些账户要在钱包里建好并**导出密钥**（用户在钱包设置里操作，属于后续阶段的用户配合项；本阶段未碰）。
- 官方示例：**未发现 Concordium 专用的端到端示例仓**；权威拼装指南就是包内 README（client/server/facilitator 三段代码齐全）+ docs.x402.org 的通用 buyer/seller quickstart（其中 Concordium signer 写法与 README 一致）。

### 2.6 路线取舍：建议 **TS 直接实现最小闭环**（路线 B）
| | A：TS 支付服务包 Python 核心 | B：TS 直接实现最小闭环 |
|---|---|---|
| 结构 | Python 结算核心（现有私有代码）+ 一个 TS 微服务只管 x402，本地 HTTP/IPC 串联 | 新仓内用 TS 实现 escrow 账本/哈希链/净额/Ed25519 收据 + x402，三件套同进程 |
| 与「干净公开仓」纪律 | **冲突**：现有核心是私有代码不能进公开仓；A 等于公开仓之外挂着私有进程跑 demo，评审看仓会缺核心逻辑，叙事别扭 | 干净：公开仓即全部 demo 逻辑，核心的「生产版」故事放 path-to-production 文档 |
| 工程量 | 多一层进程间接口 + 收据哈希跨进程绑定 + 双运行时保活 | 最小闭环逻辑本身不复杂（账本、哈希链、净额抵消、Ed25519 签名都是几百行内），且只需维护一个运行时 |
| Demo 可靠性 | 故障点多（两进程、端口、序列化） | 单进程，3 分钟视频与 Live Demo 更稳 |
| 风险 | IPC 接缝是新代码，测试基线（140 passed）覆盖不到接缝 | TS 版逻辑是新写，需自带测试；但范围小、可控 |

决定性理由：①提交纪律要求新仓干净、不能搬私有 Python 代码，A 的「复用」在公开提交里并不成立；②x402 的 ccd 实现只有 TS，TS 服务在两条路线里都跑不掉，A 只是在其上再叠一层；③评审看「深度」看的是身份/注册表/支付的结合，单体 TS 闭环把三者串得最直观。

## 3. Agent Registry 注册路线

### 3.1 入口
- **官方 dashboard：https://agent-registry.concordium.com**（Concordium 官方文章 “Visit the Agent Registry” 链接）。注册免费；Concordium Wallet for Web 本身也支持 agent 注册/管理。
- **托管 MCP 服务：`https://agent-registry-mcp.concordium.com/mcp`**（JSON-RPC 2.0），mainnet/testnet/devnet 均已配置；健康检查实测活着（2026-11-26 09:31 UTC，`GET /healthz` → `{"ok":true,"version":"0.1.0"}`）。REST 孪生端点：`GET /v1/check-badge/{badge}`、`GET /v1/get-badge-JSON/{badge}`、`GET /v1/verify-agent-card/{badge}`（无鉴权、CORS 开放、按 IP 限流）；Indexer 在 `https://agent-registry-indexer.concordium.com/`。也可本地跑：`docker run -e MCP_NETWORK=testnet … concordium/agent-registry-mcp`。
- MCP 服务**不持有任何私钥**：所有写操作工具只返回「可签名的交易载荷」，必须由调用方钱包签名提交——这是下面用户签名步骤的根源。

### 3.2 注册一个原生 agent 的五步（官方文档 “Register a native agent”）
1. `build_agent_card` 生成 Agent Card JSON + 其 SHA-256：入参为 agent 名称、描述、skills、owner 账户、托管 URL。
2. **把 Card 托管到一个公开可达的 URL**，且必须逐字节服务原文（不能重排版）——后续 `verify_agent_card` 会回抓比对哈希。载体可用新公开仓的 GitHub Pages / raw 链接（建仓后定）。
3. `build_register`（入参 `agent_uri`、`metadata_hash_hex`、sender 账户）→ 返回待签载荷。
4. **owner 钱包签名并提交** → 铸造 CIS-8004 agent NFT，拿到 `token_id`。agent 的可操作标识是其 **CIS-2 token address（Base58Check）**，MCP/REST 都以它为键（官方称之为 badge id）；DID 形式官方页面写作 `did:ccd` 前缀（完整 DID 串的拼接格式在所读文档中未给出，**标注未核实细节**，不影响注册流程）。
5. `verify_agent_card(token_id)` 确认链上哈希与托管 Card 一致（返回 `match: true`）。

Agent Card 字段（官方 “What is an Agent Card?”）：name、description、skills（id/name/description/tags）、provider、services（命名端点 URL）、**Concordium 扩展块**（CAIP-2 chain id、canonical token address、CIS-8004 与 CIS-8 合约地址、owner 账户）；Card 的 SHA-256 以 `metadata_hash` 存链上；格式兼容 A2A / ERC-8004 注册文件。

### 3.3 Verified by Concordium 徽章在 testnet 的实际发放方式
徽章不是单独一枚链上代币，而是 **Agent Card 里的一个徽章块 + 链上记录互指**：
1. agent 铸造后，用 `get_badge_json`（REST：`GET /v1/get-badge-JSON/{token address}`）取回要贴进 Card 的扩展对象、ERC-8004 `registrations` 条目与 next steps；徽章块内含核验入口 `verification.verifyUrl`（`…/v1/badge-check/{id}`）。
2. 用 `build_agent_badge` 把徽章块合并进已有 Card（不扰动其他字段），得到新 Card 与新 SHA-256 → 重新托管新 Card。
3. `build_set_agent_uri` 生成更新载荷 → **owner 再次签名提交**，把链上 `metadata_hash` 更新为新哈希。
4. 任何人可用 `check_badge` 核验：链上记录、Card 哈希、徽章块格式、核验块四项。

testnet 身份是否够用：Registry 的信任锚是「agent 的 owner 账户锚定到一个已签发身份的 credential」。用户 owner 账户的 credential 由 Concordium testnet IP 签发（§1 链上实测）；testnet 身份按官方设计就是免证件核验签发的（官方 exchange onboarding 文档：“Testnet works like mainnet, but identities are issued without verification”），且托管 MCP/Registry 对 testnet 完整配置。**故注册→挂徽章→check_badge 全流程在 testnet 上可用该身份跑通。**
保留说明（未完全核实）：官方文档未明文对比「testnet 徽章的核验状态语义与主网（真实 IP 核验）是否完全等同」；以注册当时 `check_badge` 返回的 verification block 实测为准，投稿材料里对 testnet 徽章的表述按实测结果写，不外推主网语义。

### 3.4 必须用户本人在钱包里点签名的步骤（明确清单）
MCP 只产载荷不签名，以下每一步的提交都必须由 **owner 账户**签名。当前 owner 账户在用户浏览器钱包里、助手无密钥（也不应有），所以这几下必须约用户在场点确认（或用户自行导出该 testnet 账户密钥后改脚本签——涉及私钥交接，本预研不推荐、未执行）：
1. 每个 agent 的 `build_register` 提交（买/卖共 **2 次**签名）。
2. 每个 agent 挂徽章后的 `build_set_agent_uri` 提交（共 **2 次**签名）。
3. 若要给 agent 设独立收款钱包（`setAgentWallet`，见 §3.5 的拓扑建议），每次设置另需签名 + 该钱包的 canonical bytes 证明。
其余（生成 Card、托管、build_* 载荷、verify/check 查询、徽章 JSON 获取）都是无签名的，助手可独立完成。

### 3.5 注册前还差什么（缺口）
1. **账户拓扑未建**：现只有 owner 账户 1 个。建议拓扑：owner（用户现有账户，持有两个 agent NFT）+ 买方付款账户 + 卖方收款账户 + facilitator 赞助账户（§2.3 硬约束：赞助方须独立）。后三个账户需在钱包里从 Identity 1 派生新建（用户操作，几分钟），**每个新账户第一件事是先领 20,000 test CCD**（faucet 规则：有入账后不可领，顺序不能错）。agent 与付款账户的绑定走 Card 的 services/`agentWallet` 元数据，具体绑定方式在注册阶段实测确定。
2. **签名账户的私钥导出**：x402 买方与 facilitator 要在 TS demo 里签名，需对应账户的 Ed25519 私钥进环境变量——由用户在钱包里对这几个 testnet 专用账户导出（后续阶段事，本阶段未碰）。owner 账户私钥不导出，注册签名走钱包点签（§3.4）。
3. **Card 托管地址未定**：等新公开仓建立后用其 Pages/raw 服务两份 Card JSON（须逐字节原文）。
4. **Card 内容未定稿**：两个 agent 的 name/description/skills/services 端点（services 指向 demo 的结算服务地址，本地 demo 可先用占位端点，录视频前再定）。
